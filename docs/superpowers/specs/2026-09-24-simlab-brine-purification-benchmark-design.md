# 仿真实验室 · 粗盐提纯标杆 设计

日期:2026-09-24(2026-09-25 修订,新增第 8 节;与原文冲突处已在原地标注)
状态:已与用户逐节确认。2026-09-25 用户追加两项范围决定,已回写。

范围:仅"一条完整闭合链路",首发链路仍是粗盐提纯。学科广度已确认为 5 科(见 8.2),
但那是排期目标,不是本 spec 的实现范围;账号会员与教师端分布式课堂明确不做(见 8.1)。

## 1. 定位

一个能真的把药倒错、真的让实验失败、并且能指出你为什么失败的离线化学实验台。

差异点不是"实验多",而是**判分依据来自学生自己造成的可测量后果,而不是规则条文**。
离散模型只能说"错误:液面高于滤纸边缘,扣 2 分";本系统让滤液**真的变浑浊**,
扣分依据是"你收到的滤液浊度 42 NTU"。这两种表述的可信度差一个量级,
而后者只有连续仿真做得出来。

### 商业路径(用户确认)

学生在家练操作并被当场判分 → 家长看到可提分的诊断 → 老师主动来要班级薄弱点数据
→ 学校要解决"实验操作谁来评分"时,引擎已在学生手里跑通。

**C 端成功指标不是收入,是"有多少老师主动来要数据"。**

## 2. 架构:连续呈现 + 后果判定

```
触摸手势 → ①类型化操作 → ②连续世界层 ⇄ ③物质账本层
                                      ↓ 单向读事实
                                 ④判定层 ← 细则数据文件(外置)
                                      ↓ 扣分项 + 可复算证据
                                 诊断报告 / 表现层(仅投影)
```

| 层 | 职责 | 约束 |
|---|---|---|
| ① 类型化操作 `Operation` | 手势转成带几何参数的操作事件(取药/倾倒/引流/搅拌/加热/读数/转移) | 非法参数拒绝且世界状态不变 |
| ② 连续世界 `Container`+`FluidModel` | 液面高度、倾角→流速、溢出、视线游标、火焰接触 | 不 import ArkUI/@kit |
| ③ 物质账本 `Brine` | 组分存量与转移;所有逸出/损失单独记账 | 守恒不变量在此断言 |
| ④ 判定 `Judgment`+`Rubric` | 仅在观测点读事实,按外置细则产出 `Deduction` | **永不解读意图** |

世界层直接实现已有 `IExperimentRunner` 契约,复用 `RunController` 的定步长累加、
掉帧补偿、采样与抽稀 —— 液面推进与弹簧振子同属"随时间演化的确定性世界"。

判据原语只有两种,刻意不做规则语言:数值阈值(NUMERIC,含几何量)与时序约束(SEQUENCE)。
实现时从原本承诺的三种收敛而来,理由见第 6 节末。
**评分细则的形态(离散观测点清单)决定引擎的形态。**

### 四条不变量(必须是断言)

- **I1 守恒**:`现存 + 逸出 + 损失 = 初始`
- **I2 确定性**:同一 `Operation` 序列 → 同一终态 → **同一分数**
- **I3 表现层只读**:世界与账本不 import 任何 ArkUI/@kit 类型
- **I4 细则可替换**:换 `Rubric` 文件只改变分数与措辞,不改变世界行为

I3/I4 是本架构的全部意义:判分可离线重放,不必碰真机即可验证"这个扣分对不对"。

## 3. 首发链路:粗盐中难溶性杂质的去除

选它的唯一理由:扣分点几乎全是几何量,而这些量只有连续模型能表达 ——

滤纸边缘低于漏斗口、液面低于滤纸边缘、烧杯紧靠玻璃棒、玻璃棒抵三层滤纸侧、
漏斗下端靠烧杯内壁、蒸发需搅拌防飞溅、产率与纯度可测。

液面一旦高过滤纸边缘,悬浊液就从间隙直灌,**滤液浊度真的升高**;
蒸发不搅拌,液滴真的溅出,**精盐产率真的下降**。

### 闭合的验收标准

1. 全程无一步靠"点按钮选答案"
2. 每个几何类扣分点产生可见、可测量的后果(浊度/产率/损失质量)
3. 结束时给出操作诊断报告:步骤回放 + 扣分项 + **可复算证据**
4. 判据全部来自外置细则数据文件,标注"参考细则(非官方标准)"与版本号
5. **本链路的五个验收标准全部不得依赖网络**;评分可离线重放验证。
   (2026-09-25 修订:AI 即时讲解获批联网,见 8.1。但它是叠加能力,不是本链路的前提。
   断网时这五条必须仍然成立,否则"课堂断网即不可用"会把离线这个可交付性前提赔掉。)

## 4. 测试策略

沿用 `tools/physics-check/check.mjs` 离线转译断言法(已用它抓到多个真实缺陷),扩为三类:

1. 守恒与不变量 I1–I4
2. **评分剧本回归**:把真实学生错误写成具名操作剧本,断言总分、扣分项集合、证据数值
   (`S01` 正确全流程 100 分;`S02` 未引流;`S03` 液面高过滤纸;`S04` 蒸发未搅拌;
   `S05` 量筒仰视读数;`S06` 取用超量)。任何改动导致剧本分数变化必须可解释
3. **不测画面**。视觉只能真机确认,不假装 CI 能测

真机待验清单:拖放手感、连续液面帧率、字号与触控区、大屏排版、火焰观感。

## 5. 风险(按危害排序)

| | 风险 | 缓解 |
|---|---|---|
| R1 | 参考细则不权威 | 报告首页固定标注来源与版本;`source` 字段留位,将来拿到官方细则只换文件 |
| R2 | 连续模型系数无实测依据(滤纸 bypass 率、流速、蒸发速率、溶解度) | 全部收进 `Calibration`,标注"教学演示标定值",可被细则覆盖;**断言只测守恒与单调性,绝不声称绝对数值真实** |
| R3 | 误判摧毁信任 | 判据只用两原语;拿不到事实**不扣分**(宁漏不误);每条扣分带证据 |
| R4 | 零真机验证,且**未被引用的 .ets 文件不会进 ArkTS 类型检查**(实测:带明显类型错误仍 BUILD SUCCESSFUL) | 断言全部位于数据层;bench 文件在 M4 被 UI 引用前不得声称通过类型检查;首个可运行里程碑含真机性能探针,确认手写连续液面能稳 60fps 再往上盖 |
| R5 | 鸿蒙无现成物理库 | I3 把风险关在表现层:画面最坏降级,不影响判分 |

R2 是本设计里**已知不精确**的部分,写在这里而不是藏在代码里。

### 第二次顺序调整(用户指出「缺少仿真操作的模式」)

M4-lite 的 `MeasurePage` 用**滑杆设定倾角与视线高度**。那不是仿真操作,是表单控件。

它废掉的不是手感,而是本设计自己的立论:架构主张「判分依据来自学生造成的可测量后果」。
而倾角、位置、玻璃棒在不在,现在都是我们**施予**的值 —— 学生从未做过任何空间选择,
判他「未紧靠烧内壁」就没有意义。故**直接操纵层是 M2/M3 的前置,不是并列功能**。

需要补的模型:
- `Container.pose = {x, y, tiltDeg}` + `support ∈ {HELD 手持, TABLE 置桌, CLAMPED 夹持}`
- 支撑状态本身即考点:手持才能倒、夹持才能加热;徒手拿蒸发皿天然表现为「不在架上却被加热」
- 手指轨迹抖动直接进倾角 → 流速抖动 → 溅失。真实失误来自手,不需要设计「错误选项」
- 接触类判据用容差(mm)而非像素对齐,容差进 `Calibration`

**顺序约束(用户已确认「先解锁真机,再写手势层」)**:手势是本方案唯一**完全无法自测**的部分 ——
八百来条断言测不到「旋得别不别扭」。设备未就绪前不写交互代码。当时把解锁分成两级:

| 解锁 | 能验什么 | 验不了什么 |
|---|---|---|
| A 模拟器(需下载系统镜像 + 开虚拟化) | 手势**是否触发**、坐标映射、液面跟手、布局字号、帧率 | 多指旋转的**手感**、误触、真实延迟 |
| B 真机(需华为账号自动签名) | 以上全部 + 真实手势体验与误触 | —— |

> **2026-09-25:解锁到了 A 级(模拟器),不是 B 级。** 当前 `hdc list targets` 只有一台
> `127.0.0.1:5555`,`const.product.model = emulator`。unsigned hap 可直接 `hdc install -r` 装上跑起来,
> 所以**这条路径不需要签名**。原先记录的"模拟器无镜像"已不成立;但"真机能装能跑"仍未被证明,
> 两级表里的 B 级价值(多指手感、误触、真实延迟、真实帧率)一项都没拿到。

### 一条被跳过的顺序约束(记账,不要装作没发生)

原文写的是:**"R4 决定 M5 的性能探针必须在真机可用后立刻做,不允许先堆功能。"**

真机于 2026-09-25 可用,但当天做的是首页布局整改与设计令牌收敛(第 8.3 节),**性能探针没做**。
即:手写连续液面能否稳 60fps,至今仍是假设而不是测量。这条约束的立论是"不要在没验证过的地基上往上盖",
而 `MeasurePage` 的连续液面正是那块地基。当前状态是:它进了类型检查、跑通了断言(数据层),
但帧率与掉帧补偿在真机上的实际表现未知。

**补救**:下一次真机回装时,性能探针与布局截图一起收,不另开一轮。探针最小形态 = 在 `MeasurePage`
里累计每帧耗时,连续倾倒 60 s,报 p50/p95/max 与掉帧次数。它属于 8.4 的"排版无法自测"同一批欠账。

### 8.4 验证杠杆的边界(2026-09-25 实测后重写)

本轮找到了一条**比预想强得多的排版杠杆**:`hdc shell uitest dumpLayout` 能把真机/模拟器上的组件树连
`bounds` 一起拉下来,`hdc shell uitest uiInput click` 能注入点击,`snapshot_display` 能截图。
也就是说"布局对不对"不再只能靠人眼看截图 —— 可以断言某个节点存不存在、有没有边界、标题文字对不对。
排版缺陷"点进去一片空白"就是靠这条链路定位并修掉的(见 8.6)。

仍然没有杠杆的两件事:

1. **手感与真实帧率**。当前连接的是模拟器,`const.product.model = emulator`。多指手势的手感、误触、
   真实延迟、手写连续液面的稳帧能力,模拟器给不出可信答案。R4 那条"真机可用后立刻做性能探针"仍未执行,
   而且它的前提(真机可用)也仍未成立。
2. **视觉是否好看**。树能证明节点存在与尺寸,不能证明它顺眼。

五条路由 `experiment` / `measure` / `bench` / `reactions` / `report` 全部能进对应页且标题正确。

### 8.6 白屏的根因(既存缺陷,非本轮回归)

现象:点实验列表里的实操项 → 只剩一个返回按钮的空白页,无任何 JS 异常。

根因:`@Builder routeMap(name)` 里写了**五个平级 `if`**。ArkUI 会为每个 `if` 生成一个独立容器,
而 `navDestination` 只取第一个容器的输出。`'experiment'` 恰好是第一个分支所以一直正常;
`'measure'` / `'bench'` 排在后面,第一个容器为空,目标页就成了空 NavDestination。
组件树里那个 TitleBar **没有 MainTitle 节点**,证明显示的不是页面自己的 `NavDestination` 而是占位容器。

修法:改成 `if / else if` 单链,并补一个 `else` 分支显式渲染"没有名为 X 的页面"。
这样将来任何路由名拼错都会**报出名字**,而不是再变成一次两小时的白屏排查。

这个 `routeMap` 形状在首页整改之前就是这样,所以是既存缺陷;之前没暴露是因为没人点到过实操项。

### 8.8 本地持久化与历史回看(2026-09-25 落地)

第 3.3 条验收标准(结束时给出诊断报告)此前是**假闭合**:`ReportPage` 每次进入都重跑一遍
规范示例 `BrineScenario`,扣分列表恒为空,没有任何一次真实操作留下痕迹。关掉应用等于什么都没发生。

补上的三层:

| 层 | 文件 | 为什么这么切 |
|---|---|---|
| 数据 | `model/SessionRecord.ets` | 事实存成 `FactEntry[]` 而不是 `Map` —— Map 过 JSON 会变成空对象,读数静默清零 |
| 逻辑 | `runner/SessionLedger.ets` | 排序、上限 50 条、按实验统计、序列化。**纯逻辑,不 import 任何 @kit**,所以全部可离线断言 |
| 落盘 | `platform/SessionStore.ets` | 全工程唯一 import `@kit.ArkData` 的文件,只读写一对 Preferences 键值,没有可测逻辑 |

两个设计决定值得记下来,它们都不是风格问题:

1. **`awarded` 序列化成字符串而不是数字。** `JSON.stringify(NaN)` 写出 `null`,反序列化端一个
   `Number(null)` 就把「未评分」变成「考了零分」—— 这是最难发现的那类错误,因为它看起来是个合理的分数。
   变异检查确认:把 `awardedOf` 对 `'nan'` 的返回改成 `0`,断言「未评分往返后仍是 NaN,不是 0」立即失败。
2. **只存观测到的数,不存结论。** 分数由判据在回看时按当时的细则重算。把分数存死,细则换版本后
   历史记录就和判据脱钩了,违反不变量 I4。

写入点:量取训练的「收手判定」。读取点:报告页新增的「历史操作记录」段。
`loadHistory()` 挂在 NavDestination 的 `onAppear` 而不是 `aboutToAppear` —— `getUIContext()` 要求
组件已挂到某个 UI 上下文,`aboutToAppear` 时这一点没有保证。

实测证据(模拟器):跑一次量取 → 收手判定 → 界面显示「已保存 1 次操作记录」→ `aa force-stop`
杀进程 → 重启 → 报告页显示该条记录(标题、`goalMl 10.00 · actualMl 0.00 · readMl 0.00`、用时 4 s)。
再次覆盖安装后记录仍在。

**同时新增一条架构护栏**:`check.mjs` 断言全工程 `@kit.*` 导入集合等于白名单,并显式断言
NetworkKit / AccountKit 等未出现。向 `Contrast.ets` 注入一行 `@kit.NetworkKit` 的变异测试确认它会拦。
这条护栏存在的理由正是 8.1:离线承诺现在会被 AI 讲解部分放宽,放宽必须是**一次被记录的决定**,
而不是一个顺手的 import。

仍欠的:事实键显示的是内部名(`actualMl` 而不是「实际量取」)、无按日期分组、无删除。
历史条目**现在**有分数了,见 8.9。

> **2026-09-26 更新**:事实键显示名已由 `FactLabels` 解决;分组与删除见 8.19。三条全部闭合。

### 8.9 量取参考细则(让历史记录带分)

`bench/RubricMeasure.ets`,两条判据合计 100 分,`source` 与 `version` 沿用提纯细则的标注方式:

| | 判据 | 算子 | 事实 | 阈值 | 分值 |
|---|---|---|---|---|---|
| M01 | 量取偏差超出允许范围 | ABS_GT | `deviationMl` | 0.5 mL | 70 |
| M02 | 倾倒过程洒失 | GT | `spilledMl` | 1.0 mL | 30 |

**为什么只有两条,而且视差不单独扣分。** 原本想加第三条「读数与实际不符(视差)」,但学生
「倒到自己以为到达目标为止」这个典型动作下,`readErrorMl` 与 `deviationMl` 是同一个错误的两面:
读数偏小多少,就少倒多少。两条都判等于同一个错扣两次。R3 是宁漏不误,所以视差数值只进
**证据文本**,让学生看见原因而不重复扣分。

**分数不写进记录。** `SessionRecord.awarded` 刻意留 NaN,回看时由 `Rubrics.byId(rubricId)` 找回细则、
`Rubrics.factsFor(record)` 派生事实、`Judgment.score` 重算。存死分数会让历史记录在细则换版本后与判据脱钩,
违反不变量 I4。派生量(`deviationMl`、`readErrorMl`)也不进记录,在桥接层算。

`Rubrics.factsFor` 对**认不出的细则只做原样搬运**,不替它编派生量:派生错了会产出看起来合理但无依据的扣分。

实测(模拟器,一次真实的倒歪):目标 10 mL,仰角拉到约 40° 后实倒 8.98 mL、洒失 0.89 mL、
自报读数 7.00 mL。报告页历史段显示
`得分 30 / 100(参考细则(非官方标准) 2026.09-draft1)` + 扣分项「量取偏差超出允许范围」。
洒失 0.89 低于 1.0 阈值,**没有**产生 M02 扣分,与判据一致。
同页上一条在细则落地之前写入的记录显示「未评分(没有匹配的参考细则)」,是预期的降级而不是错误。

断言 877 → 908,其中 31 项属这一节:细则合法性、分值合计、双判据不重复扣、完美操作满分、
事实缺失一律放过、同记录重放分数一致、派生分发、未知细则不产出派生量。

### 8.10 粉末取用与"不新增判据"的后果闭环

`bench/Spatula.ets`:药匙或纸槽取粉末状固体,考点是「一斜二送三直立」。

这是首发链路(粗盐提纯)真正缺的第一步 —— 取粗盐。此前 `BrineScenario` 直接调
`Separations.addCrudeSalt`,投料没有操作语义,等于"盐凭空出现在烧杯里"。

**模型**:沾壁量与撒落量由两个因子决定 —— 药匙末端到落点的自由下落路程,和容器轴与水平面的
夹角(`sin`,直立为 1、横放为 0)。送到底 + 横放 ⇒ 两项皆零;直立浅取 ⇒ 撞壁并撒落。
两个占比系数是教学演示标定值(与 R2 同类),**可信的是守恒与单调关系**:送得越深沾壁越少、
越接近横放沾壁越少。20 种姿态组合逐一断言三项之和精确等于投料量。

**账本**:新增 `saltStuckG` 与 `sandStuckG` 两个存量(七个存量互斥且完备,都进 `mass()`)。
刻意不并进 `saltSolidG` —— 并进可溶存量等于把操作失误从账本上抹掉。分开的直接后果是
`dissolve()` 天然不吃它:沾壁的盐**不参与溶解**。

**关键设计决定:不为这个失误新增判据。** 沾壁 → 少溶 → 产率下降 → 既有的 B06 产率判据命中。
剧本 S07(直立、没伸进去)实测:沾壁 1.68 g / 4 g,产率从 100% 掉到 58%,
`fired` 集合精确等于 `'B06'` —— 一个都没多。这正是第 2 节架构主张的兑现:判据读的是**后果**,
不需要为每种新失误加一条规则。反过来,如果每发现一个考点就要新增判据,说明世界模型不够连续。

默认参数是规范动作(横放 + 送到底,沾壁为零),所以 S01–S06 六条既有剧本**一条没动**就全绿,
这本身是行为保持的证据。

断言 908 → 974。两处变异检查:把沾壁盐并进 `saltSolidG`、把撒落漏记损失账,分别被
「沾壁的盐一点没溶」「账本守恒」等 12 项抓出。

**过程中两个自己制造的错,记下来避免重犯**:
1. 在 `emitFacts` 里重复写了 `undissolvedAtFilterG`,会用蒸发之后的值覆盖第 92 行在**过滤时刻**
   记的正确值,破坏 S02 断言。跑验证台才发现。时刻敏感的事实必须在事件发生时记,不能在汇总时补。
2. S07 的不等式一开始写反了(声称产率损失 ≤ 沾壁占比)。实际必然 ≥ ,因为沾住的盐不可能回收,
   而还有额外溅失。是实现没错、测试错,按"改代码不改断言"的规矩核对后修正了断言方向。

### 8.11 报告页主段改由选中记录驱动(3.3 条真正闭合)

此前 `ReportPage` 的分数、扣分、事实表、步骤时序四段全部来自 `aboutToAppear` 里跑的规范示例,
**第 3.3 条验收标准是假闭合**。现在:

- `loadFrom(card, label, showing)` 完全由传入的 `ScoreCard` 驱动,事实表**遍历 `FactSheet` 自己的键**,
  显示名查 `model/FactLabels`。原来硬编码的 12 个提纯键被删掉 —— 那是换链路就整表静默变空的隐患。
- 点历史行 ⇒ 主段换成那次操作并滚回顶部(段在屏幕下方而变化发生在顶部,不滚用户看不到)。
- 有真实记录时进入页面即自动选中最新一条;规范示例只在没有记录时占位,且标题下明确写
  「规范示例,非你的操作」。**页面永远说清你看的是谁的分数。**

`model/FactLabels.ets` 是一张键到「显示名 + 单位」的集中表,配 41 项断言,其中最有价值的一组是:
**遍历提纯与量取两条链路实际产出的每一个事实键,断言它配了显示名**。以后加新事实忘了配标签,
断言会指名是哪个键,而不是等截图发现表格里有 `actualMl`。单位里的前导空格是刻意的:
`88.50%` 不加,`4.00 g` 要加。查不到的键退回键名本身而不是空串 —— 宁可难看,不要静默消失。

### 8.12 化学器皿改用软件回转体渲染(2026-09-26)

用户决定"操作仪器以 3D 形式存在",又明确"跳过 spec 直接实现化学回转体"。ArkGraphics3D 在这台模拟器上
渲染不出任何东西(见 5 节 R4 与记忆里的探针记录),而量筒、烧杯、试管、锥形瓶、漏斗、蒸发皿**全都是回转体**:
回转体在正交投影下的外形由一条母线加一个圆环唯一确定,明暗只依赖方位角的余弦。于是自己算,不建网格不上 GPU。

| 文件 | 职责 | 可断言 |
|---|---|---|
| `bench/Profile.radiusAt()` / `revolve()` | 半径是截面积的解析逆;半球底、锥体加细颈由半径函数离散成同一张分段表 | 是 |
| `view3d/Camera` | 俯仰正交投影、椭圆扁率、`widthGain` 可读性加宽、`Ring.pointAt(φ)` | 是 |
| `view3d/Lathe` | 只读 Profile 的母线采样 + Lambert 明暗带 | 是 |
| `view3d/LathePainter` | 轮廓、渐变、液面、刻度、判读线 | 刻意做薄,只有 `fitFor`/`ticksFor`/`tone` 公开出来被钉 |
| `view3d/VesselShapes` + `VesselView` | 器材种类→显示剖面;组件持有自己的 Canvas 上下文,`@Prop @Watch` 驱动重绘 | 形状映射可断言,画面不可 |

三条不是风格问题的决定:

1. **宽度与容积同源。** 渲染层要宽度只能问 `Profile.radiusAt`,因为 `area = πr²`。否则"画出来的形状"
   和"算出来的液面"迟早对不上,而液面正是判分的依据。
2. **`widthGain` 是承认可读性折衷。** 10 mL 量筒名义截面只有 2/3 cm²(直径不足 1 cm),按真实比例画
   就是一根看不出刻度的线。水平方向整体乘同一个数:截面之间的相对宽窄一分不少,所以仍是同一条曲线。
3. **份制容器不画分度。** 实验台的容量是标定份数(见 R2),画任何刻度线(哪怕不带数字)都在暗示一套
   不存在的量程。形状借给它们,数字不给。

`fitFor` 公开的两个理由都被断言兑现:画出来一定不出框(4 种器皿 × 5 种画布 = 80 项)、加宽不改变口底
宽度比。器底改为坐画布下沿 —— 各自垂直居中会让矮的器皿在并排时"浮"起来。

变异检查做了五轮:去掉 `widthGain`、`pointAt` 的 sin/cos 互换、分度不做整数吸附、`baseY` 贴回居中公式、
`hx()` 不补零 —— 分别被 2 / 8 / 7 / 8 / 8 项指名报错。**`pointAt` 那 8 项最值**:相位写反只会让画面
"看着怪",没有任何其他手段能发现。

### 8.13 一整类静默失效:`@Builder` 按值传参(2026-09-26 抓到三处)

### 8.15 滴加与块状固体的后果模型(2026-09-26,模型已就位、尚无调用方)

`bench/Dropper.ets` 与 `bench/ChunkSolid.ets`,与 `Spatula` 同一形状:输入只有几何与朝向,
输出是**分账**,不含意图字段。断言 1243 → 1439(新增 196 项),六轮变异各被 1–22 项指名抓出。

**滴加**把滴管里那份液体分成四处,之和恒等于计划体积:`delivered / stuckWall / splashed / reflux`;
`carriedBack` 单独记 —— 它是尖端从**容器里**带走的液体,混进滴管的账会让人把"交叉污染"读成"损失"。
三个考点各自对应一个可测量:伸入或碰壁 → 带回量与挂壁量;胶头朝下 → 倒流量;滴得过高 → 溅出量。
**规范姿态必须精确地四项全零**(悬空约 1 cm、不碰壁、胶头朝上),否则"失误"没有对照基线。

**块状固体**「一横二放三慢竖」的考点是砸破管底。`bottomDamage` 取 0..1 的连续损伤量而不是布尔:
「裂而未破」与「砸穿」在真实操作里都存在,而连续模型正是本项目相对离散仿真的立论。
关键输入是 `verticalDropCm`(落到器底前的**竖直**落差)—— 横放管口再慢竖,块体沿壁滑下,
落差只有一个管半径;直立从管口松手,落差就是整个管长。这一个量把"慢竖"和"直投"分开了,
而模型不猜它,由知道容器姿态的那一层算出来。

**没有接调用方,而且这是刻意的。** 三条理由:

1. 接进**粗盐提纯**不真实 —— 那条链路里没有块状固体,滴加也不是它的步骤。
2. 接进**实验台**需要容器有几何与漏失账:`BenchModel.Vessel` 目前只有份数,
   这正是 M4(`Vessel` 并入 `Container`)没做的部分。
3. 接进**量取页**的定容步骤(教科书里确实有「改用胶头滴管滴至凹液面齐平」)需要一个滴管控件,
   而用滑杆或按钮冒充操纵是本项目明令禁止的(见"第二次顺序调整")。

因此这两个模型现在的身份是**已断言、未接线**的原件。代价必须说清楚:
**它们没有经过 ArkTS 类型检查** —— 编译缓存里 `Dropper.ets` 与 `ChunkSolid.ets` 计数为 0,
离线台架用的是 DevEco 自带 TypeScript 的转译,抓不到 ArkTS 特有的类型规则。
第一个真实调用方落地时必须顺手补这条(接进 UI → 复算缓存计数)。

### 8.16 M4:两套容器合并外壳(2026-09-26)

第 7 节写的「`BenchModel.Vessel` 并入 `Container`」**按字面做是错的**。探索两边之后发现,
两套账本不是同一件事的两种写法:`Brine` 按**相**记账(水 / 已溶盐 / 未溶盐 / 沾壁 / 悬浮砂 / 沉底砂,
随溶解、沉降、过滤、蒸发演化),`Content[]` 按**试剂键 → 摩尔**记账(随化学计量反应演化)。
强行并成一套要么丢掉整张反应表,要么给 NaCl 编出一个不存在的试剂键。

真正重复的只有**外壳**。所以:

| 单元 | 内容 | 谁用 |
|---|---|---|
| `bench/VesselBase.ets`(新) | `profile / pose / support / stirred / damage` + 纯几何算法,一律**收体积作参数**(`liquidHeightFor(volumeMl)`) | 两侧 |
| `bench/GlassShapes.ets`(新) | 器材种类字符串 → 回转体几何,带缓存;认不出的种类退回试管而不是空剖面 | 两侧 |
| `Container extends VesselBase` | 只留 `brine`,原方法改为委托 | 提纯链路 |
| `Vessel extends VesselBase` | 只留 `contents / escaped / leaked / heated / powered / capacity` | 反应链路 |

三个决定值得单独记:

1. **外壳算法收参数、不收账本。** 外壳一旦直接读 `brine.waterMl`,就再也给不了反应链路用,
   合并会退化成一个共享基类加两份复制粘贴。
2. **漏失必须由账本自己按比例取走。** 外壳只算 `leakFraction()`(即损伤程度),
   `Container.drainFraction` 走 `Separations.leak`,`Vessel.drainFraction` 走 `Contents.leakInto`。
   漏失若凭空减库存,I1 当场破掉 —— 而反应链路此前**根本没有守恒断言**,M4 是第一次给它加上。
3. **`damage` 同时就是漏失比例**,不再另设一个漏失系数:少一个系数就少一处拍脑袋。
   `Separations.leak` 只漏**可流动**的部分 —— 沾在器壁与容器口上的 `saltStuckG / sandStuckG`
   在裂缝上方,物理上不会顺壁流进裂缝。这条是写断言时逼出来的:不分开,
   「沾壁」这个后果会被漏失冲淡,两条失误在账上再也分不开。

**换 kind 必须走 `setKind()` / `Vessel.of()`**,否则几何会停在旧形状上,而落差、液面、容量全跟着几何走。
`view3d/VesselShapes.ets` 因此删掉:几何一旦进模型,查表留在视图层就成了模型依赖视图。

**验证**:断言 1439 → **1466 全过**,其中**原有 1439 条一条未动** —— 这就是「外壳合并没改变行为」的证据
(与 8.10 里 S01–S06 一条没动同一个道理)。新增覆盖:落差只由倾角与轴向距离决定(横放精确为零、
30 度取一半、非法输入不产出 NaN)、损伤即漏失比例、提纯账本漏失前后 `totalAccounted` 不变、
沾壁的料一点没漏、漏失不混进溅失账、反应链路「现存 + 逸出 + 漏出 = 加入量」。
三轮变异(漏走不进账、落差忘乘 sin、漏出不搬进 leaked)分别被 3 / 3 / 2 项指名报错。
构建绿;`VesselBase` 与 `GlassShapes` 编译缓存计数均为 1。
模拟器实测:三只容器的形状、液面、质量与合并前一致,器底仍在同一台面,无回归。

**仍然欠的**:`Dropper` 与 `ChunkSolid` 的编译缓存计数还是 0 —— M4 备好了几何与漏失账,
但还没有把它们接进任何操作。那是 #35。

### 8.18 圆角与内边距收敛:以及为什么 `space:` 停手(2026-09-26)

接 8.17 留下的下一层债。这轮动的是 27 处圆角 + 16 处单参内边距。

**驱动它的不是"数字不好看",是同角色漂移**:动作按钮同时在用 `9 / 10 / 10` 三种圆角
(`BenchPage.action`、`ExperimentPage.transportButton`、`MeasurePage` 三个整宽按钮),
卡片在 `12` 与 `14` 之间摇摆,卡片内边距出现 `8 / 10 / 12 / 14 / 16` 五个值。
同屏两张卡片差 2vp 说不清为什么 —— 这才是阶梯存在的理由。

**新增角色只有一个**:`controlRadius = 8 / 8 / 12`,比卡片低一档,因为控件嵌在卡片里,
同值会让"里"和"外"读起来是同一层。守卫断言 `cardRadius >= controlRadius` 且控件圆角落在阶梯上。

**另两类圆角不该是阶梯成员,而是自身尺寸的一半**:8×8 的学科色点(圆角 4 = 正圆)、
12×3 的图例色标条(圆角 = 半高 = 胶囊)。它们写成字面量时,改尺寸会忘记改圆角,
所以源码里直接写 `Layout.dotSize() / 2`、`Layout.tickHeight() / 2` —— 派生关系进代码,不进注释。

### 8.19 历史管理:删除与按日期分组(2026-09-26,补完 8.8 欠的两条)

### 8.20 界面在描述一个不存在的动作,以及 M6 真正的阻塞点(2026-09-26)

找 M6 的切口时撞上的:量取页状态行写的是「倾倒中…松开仰角可停」。可仰角是**滑杆**,
没有"松手"这回事 —— 滑杆的值停在哪儿就是哪儿,要停得去按「暂停」。界面在教学生做一个
不存在的动作。

改成由物理侧给数的两句话(`onsetDeg` 本来就是 `BenchWorld.readObservable` 的一个观测量,
所以页面不复制那个 12):

- 仰角低于起倒角:`倾倒中·仰角未到 12°，暂无液流`
- 仰角不低于起倒角:`倾倒中·仰角降回 12° 以下即停`

**顺带暴露了一个更实在的缺陷**:学生按「开始倾倒」时如果仰角还是 0,`PourModel.flowRate` 返回 0,
量筒里什么都不会多 —— 而界面上既没有瓶子也没有任何解释,只有读数死死停在 0.00 mL。
现在这句话会直接告诉他为什么。模拟器实测两个分支都对:0° 时停在 0.00 mL 并显示「暂无液流」,
拖到 44° 后换成另一句、实际量取涨到 7.38 mL、你的读数 5.76 mL(视差是这一关要考的)。

**M6 真正的阻塞点查清了,不是设备而是渲染器。** 要把仰角从滑杆换成手势,前提是先能画
「一只倾斜的瓶子,而液面仍然水平」。现有 `LathePainter` 只在自己的正立坐标系里画液面;
把整块 Canvas 用 `.rotate({ angle })` 转过去,液面会跟着玻璃一起歪 —— 在这款教实验操作的应用里
那是**错误画法**,不是"不够好看"。所以 M6-a 的前置是给 `LatheSpec` 加 `tiltDeg`、
让液面在世界坐标系里保持水平,要动 456 行的绘制器与它下面 `Camera`/`Lathe` 的核心几何。
这一条不该以半成品交出去,故本轮没做。

**化学台这边是同一个问题的另一面。** 拖放本身是真的(`draggable` + `onDragStart` + `onDrop`),
但 `BenchEngine.pourInto` 是**全有或全无**的搬运:一次倒光、不留残液、不洒、不沾壁。
`Dropper` 与 `ChunkSolid` 至今零调用方,缺的不是那两个模型(它们已经建好并被断言覆盖),
而是这条链路上根本没有「过程」这个概念 —— 只有"倒完了"这一个瞬间。
所以 #35 / #8 的前置应从「M6 手势」改写为「链路里要有可承载过程量的中间态」。

**本轮验证**:1590 项断言全过(未新增,这条改动没有可断言的纯逻辑);构建绿;
模拟器实测状态行两个分支、倾倒过程、液面与读数标记均正常。

### 8.21 倾斜液面:一份外部方案的核实结果,与切片 1 落地(2026-10-07)

用户贴来一份「SimLab 综合演进方案(整合 7 轮调研)」,要求先理解再动手。核实分两半。

对应的现状也查了:全项目搜不到 `@kit.ArkWeb`/`XComponent`/`ArkGraphics3D`,是绿地。

**但它关于代码的说法基本站得住**:ExperimentRegistry(`runner/ExperimentRegistry.ets:19`)、
RubricValidator(`bench/Rubric.ets:137`)、ReactionValidator 三重守恒校验
(`chemistry/ChemistryLibrary.ets:11`)都在。它列的最高优先项 1.1「LathePainter 倾斜液面」
与 8.20 独立量到的结论是同一件事 —— `view3d/LathePainter.ets` 456 行里
`tilt / incline / rotate / angle` **一个都没有**。
只有一处不对:方案说的不是"修复"而是"新造" —— 它提到的 pH 在代码里没有对应物,
化学模块只有 `'指示剂'`、`'滴定'` 这类条件标签和一句现象文案,没有 pH 这个量。

**推导之后,切片 1 需要的几何比方案设想的少一整套。** 器坐标 (h, ρ, φ) 绕屏幕横轴倾 α:

- 世界高度 `Y = h·cosα − ρ·cosφ·sinα`
- 投影 `screenY = −h·cos(θ+α) + ρ·cosφ·sin(θ+α)`

第二式与 `Camera` 现有的正交投影式**逐项相同**,只是俯角换成 θ+α。
所以"双 canvas 合成"其实不必:器身、刻度、明暗全部照旧画,只把俯角加上倾角即可,
需要重算的只有液面 —— 一个 canvas、一套既有几何。这一点直接影响 M6 的工作量估计。

液面本身:每个截面圆盘被一条直线割成两块,割线到圆心的有向距离
`d(h) = (h·cosα − Z)/sinα`,浸没的那块是一个**圆缺**,体积就是圆缺面积沿轴线累加。
新增 `view3d/TiltedPlane.ets`,三个纯函数:`segmentArea` / `volumeBelowPlane` / `planeForVolume`,
不 import 任何 `@kit`(I3)。α=0 直接委托回 `Profile`,保证不倾斜时画出来的液面
和判定层算出的液面是同一个数。断言 **1590 → 1842**。

**本轮抓到的四个仪器问题,都记下来,因为它们和下次的误判同源。**

1. **两条单调断言是假的。** 扫掠里写的是 `if (a > prev) bad = false`,而桩函数返回 NaN 时
   两边比较都不成立,断言**真空通过** —— 8.19 那次同类错误的翻版。补 `Number.isFinite` 才成立。
2. **`segmentArea` 被钉死在五个退化点上。** d=0 时公式第二项本身就是 0,d=±r 走的是提前返回,
   所以把 `- t√(1−t²)` 写成 `+` 的变异**全套跑绿**。补了三条独立判据:能手算的非退化点
   (d=r/2 时 A = 4π/3−√3,r=2)、200000 步中矩形积分对照、以及恒等式 A(r,d)+A(r,−d)=πr²。
3. **我自己先写了一条站不住的连续性断言。** 本以为 α→0⁺ 会收敛到 `Profile.volumeBelow`,
   实际不会:压在段界上的那张盘面被斜平面**平分**,而 `heightForVolume` 的线性插值不计它,
   两者天生差半段。诚实的断言是「起倾瞬间自由面错开不超过一段(0.1 cm)」,
   这条反倒更严 —— 它同时钉住了段内取点用段底而不是段中。
4. **`BUILD SUCCESSFUL` 不是新模块的证据。** 构建绿、`CompileArkTS` 真跑了 32 s,
   但 `TiltedPlane` 的编译缓存计数是 **0** —— 还没有任何模块 import 它,ArkTS 不编译不可达文件。
   8.20 之前那套"逐文件缓存计数 = 1"的审计口径,只覆盖可达模块;新模块必须接线之后才算验过。

**变异测试**:13 条,全部被抓(圆缺符号、取点段中、d/r 倒置、满盘写成半盘、丢 sin<0 翻转、
平面高度符号反、二分方向反、半径忘开方、二分次数 48→8、α=0 特判永不触发……),
文件还原后 md5 校验一致。

**还没做的。** 切片 2 = 液面的**画**法:沿方位角 φ 的母线上湿界高度
`H(φ) = 最大的 h 使 Y(h, r(h), φ) ≤ Z`(自顶向下扫段,不需要求根器),以及液面从**器底**
而不是器壁穿出时那一片补块(小体积 + 大倾角就是这个形态,正是倾倒过程最常见的那一段)。

### 8.22 切片 2 落地:器壁是台阶,所以"液面水平"只能量到台阶精度(2026-10-07)

新增 `TiltedPlane.surfacePoint(profile, tiltDeg, planeWorldCm, phiDeg) → { hCm, radiusCm }`:
给定方位角,返回液面边界贴在器壁上的那一点。断言 **1842 → 2047**。

**做法上没有用到求根器。** `Profile` 的半径本来就是每 0.1 cm 一段的常量表,所以每段内
`Y(h) = h·cosα − r_i·cosφ·sinα` 是斜率 `cosα > 0` 的直线,段内交点解析可解:
`h* = (Z + r_i·cosφ·sinα) / cosα`。试管半球底那种"先降后升"的母线也不用特殊处理 ——
逐段取候选再比大小就够了。

**第一次写错的地方很值得记。** 我先按"自顶向下,第一个交点在本段之上就说明这条母线全湿"来写,
这在直筒上对,在**斜壁**上错:锥形瓶收颈,`r` 随高度下降,`h*` 却随 `r` 增大,
于是在中段解出 `h* > 段顶` 时,真正的原因是下一段的半径台阶把 `Y` 顶过了 Z。
症状是那 8 个方位直接掉进"器底穿出"分支,返回 `(0, 0)`,共面性差 5.2 cm —— 液面会画到器外去。

**台阶是模型本身,不是缺陷,所以判据也要按台阶写。** 器壁轮廓本来就是 0.1 cm 的台阶函数
(`Lathe.radiusAt` 画的就是它),因此"最高湿润点"的世界高度与 Z 天生差**至多一个台阶宽**:
实测界是 `max|r_i − r_{i−1}| × |sinα|`(锥形瓶 40° 台阶 0.0335 × sin40° = 0.0215,
实测最大偏差 0.01996)。把共面性写成 `1e-6` 会既测不出真错、又长期红着一个不存在的 bug。
最终三条判据:① 共面(误差在一个台阶内);② 不出器身;③ **其上再无湿润点** —— 这条是
"最高"的精确定义,不带容差,也是三条里最硬的。

**切片 1 补了一条独立校准。** 轴向切片积分与极坐标二重积分(400×720 中点式,完全不共用代码)
算同一个平面切出的体积:0.1 分段差 0.63 mL、0.01 分段差 0.063 mL,一阶收敛到解析值 87.08 mL。
原判据写的容差 0.05 会红 —— 那不是算法错,是被测实现自己的粒度。改成"细分段的误差比粗分段
小一个量级"这种收敛形式,才是能站住的说法。

**两条变异活了下来,查出都是我写了不会发生的分支,已删:**
- `bestH > total ? total : bestH` 的钳位:`hit < high ⟸ Z < yHigh` 代数上恒成立,`bestH ≤ total` 是定理。
- `surfacePoint` 里的 α=0 特判:`sinα=0` 时偏移项直接为 0,通用循环逐位给出同一个数
  (删掉后 2047 条全绿,这就是证据)。`volumeBelowPlane` 那个特判**必须留**,因为那里要除以 sinα。

**变异复测**(简化后重跑):取第一个交点而非最高 → 61 红;丢掉"整段全湿"分支 → 26 红;
偏移项符号反 → 37 红;段内交点改回段底 → 31 红。比简化前抓得更多。
另补 90° / −90° 的极端用例:此时 `cosα=0`,通用式里那处除法必须证明取不到 —— 全绿。

**仍欠的:** 切片 3(接进 `LatheSpec.tiltDeg` / `VesselView` / `MeasurePage`,模拟器截图确认液面水平),
以及 8.21 第 4 条记下的 **`TiltedPlane` 编译缓存计数 = 0、尚未经过 ArkTS 检查** —— 接线前它只是离线验过。

### 8.23 切片 3 接线:瓶子终于出现在屏幕上(2026-10-07)

**渲染侧的结论先说:倾斜不需要第二块画布。** 上一轮推导出的投影恒等式在这里兑现 ——
`fitFor` 只把俯角从 θ 换成 θ+α,器身、刻度、明暗、内外壁全部原样复用;
只有液体换成 `TiltedPlane` 切出来的多边形。改动集中在 `LathePainter`:
新增 `LatheSpec.tiltDeg`(默认 0)、`fillTiltedLiquid` / `drawTiltedSurface` / `surfaceArc`,
并把 `fillBand` 里的渐变那段抽成 `paintBody`(正立与倾斜两种轮廓共用,不复制粘贴)。
`LatheSpec.tiltDeg = 0` 时代码路径与接线前逐位相同,这条不是推测,是断言(见下)。

**俯角上下限是新加的教学约束。** `MIN_VIEW_ELEVATION = 4`、`MAX_VIEW_ELEVATION = 80`:
投影椭圆的高低比是 sin(俯角),平视塌成一条线、正视压成一张饼,两端都画不出体积感。
超出这个区间的倾角属于"真的需要 3D",不在回转体这套里硬撑。

**8.20 记的那个缺陷补上了:量取页现在有试剂瓶。**
之前学生拖「倾倒仰角」时屏幕上什么都不变,界面在说一件没发生的事。现在量筒左边站一只瓶子,
按同一个角度歪,瓶里的液面留在世界水平面上,倒掉多少就矮多少。
新增的都是只读投影:`BenchWorld.reagentProfile() / reagentVolumeMl() / reagentTiltDeg()`,
以及 `Layout.bottleWidth / bottleHeight` 两档尺寸。
**倾角取 `pose.tiltDeg` 而不是滑杆瞬时值** —— 画出来的角度和 `flowRate` 用的角度必须是同一个数,
否则界面画的是一次倾倒、判的是另一次。

**新造了一件工装:`tools/physics-check/record-ctx.mjs`。**
它是记录型画布,把 `LathePainter.draw` 的每一次落笔按路径记下来,于是"只能靠眼睛验"那一层里
有四件事现在能断言:空路径上没有 fill/stroke、每次落笔都在画布内、
同一份状态画出逐位相同的落笔序列(**确定性 I2 也要管渲染**),
以及倾斜时液面真的是"闭合折线填过又描边"那一条。断言 **1842 → 2093**。

**这一层照样抓到两条假断言,是同一族错误的第三次:**
1. 第一版判"路径没闭合就画" —— 但 Canvas 里 `beginPath` 丢弃上一条路径是正常用法,
   未闭合不等于错,判据本身定义错了。
2. 第二版按"折线够长且闭合且填充"认液面 —— "液面折线整条丢了"和"忘了 closePath"两个变异
   **全都跑绿**,因为液体本体那条路径本来就满足条件,把判据顶替满足了。
   改成认"填过**又描边**的长折线",并且双向判(倾斜时恰好 1 条、平放时恰好 0 条),
   四个变异才各自只红 1 项。

**这一轮还差点交出一句假话:** 构建 `BUILD SUCCESSFUL` 之后我准备写"ArkTS 已验过",
但 `TiltedPlane` 当时还没有任何调用方,编译缓存计数是 0。接线后复测:
`TiltedPlane` / `LathePainter` 缓存命中各 3,`MeasurePage` / `Layout` / `BenchWorld`
的编译产物时间戳都晚于源码改动 —— 8.21 第 4 条欠的账到这里才算还清。

**设备实测还没做。** 模拟器此刻离线,而起它要动那个长驻宿主进程(会顶掉在跑的设备实例),
需要用户点头。所以**液面在像素上真的水平、瓶筒并排不重叠、z 序没有把液体压在玻璃下面**,
这三条目前只有几何与落笔坐标层面的证据,没有截图证据。渲染顺序这一类问题离线断言抓不住,
必须看一眼屏幕。

### 8.24 设备实测:瓶子确实歪了,而我设计的像素判据不成立(2026-10-07)

用户批准起模拟器后跑完整轮:装 HAP → 进量取页 → 拖「倾倒仰角」→ `snapshot_display` 取图。
断言 **2093 → 2102**(夹位与倾角上限改了判据,并把落笔检查扩到 76°/90°)。

**第一张图就推翻了我自己写的注释。** 76° 时瓶子与 0° 逐像素相同。两个独立原因叠在一起,
少修一个都还是不动:

1. `reagentTiltDeg()` 取的是 `pose.tiltDeg`,而它只在 `step()` 里从参数派生 —— **暂停时永远是 0**。
   改成取输入参数:参数才是这一帧的真值,而 `flowRate` 下一迈读的也是它,两边不会分家。
2. 更隐蔽:`setSlider` 的倾角分支**直接 `return`,没调 `refresh()`**(视线那条有调)。
   Canvas 不会自己重画。这条早先写下来是合理的——当时屏幕上确实没有东西跟着仰角变——
   于是又长成 8.20 那个形状:**界面上有一个能拖的数,而画面不响应它**。

**改完实测:** 0° / 39° / 76° 瓶子跟着滑杆连续变歪 ✓;倾倒链路通(实际 4.73 mL、读数 3.69 mL、
读数位 5.5 cm、暂停按钮与状态行同步)✓。另外把试剂瓶从**满瓶**改成**七成**:满瓶一歪,
液面就被器沿夹住,"液面保持水平"这件事在屏幕上永远看不见 —— 而一瓶试剂本来也不该灌到瓶口。

**滑杆量程是 0..90,不是我假设的 60。** 原来把可视俯角夹在 80° 以内,后果是
"数字还在涨、画面不再动",又是同一类界面说谎。上限改到 86°:此时瓶口几乎正对观察者,
画成一枚近圆就是它该有的样子;再往上(要看见侧倒的器身内壁)才是回转体这套的边界。

**我自己设计的像素判据不成立,这一条最该记下来。** 我量的是"液面与左右母线两个切点同高",
39° 实测两端 y 差 4 px(0° 时差 2 px),看着漂亮。跑完才想清楚:
**器身坐标系里任何一圈等高环投影出来,左右切点本来也同高** —— 所以"液面跟着玻璃一起歪"
这个我正要排除的错误画法,同样满足这条判据。它不判别,那 4 px 是仪器自己的功劳。
能区分的量是**近壁爬高、远壁降低的不对称**(等高环给不出不对称),
以及液面椭圆的竖直跨度(水平面 ≈ `rx·0.417`,等高环 ≈ `rx·0.857`,差一倍)——
但截图上还有 1.4 px 描边、凹液面、玻璃与投影阴影,用 JPEG 硬量这个不划算,脚本已删。
**结论:液面水平性的证据仍在离线那 2047 条共面断言里(每个边界点世界高度恒等于 Z,11 条变异全抓);
设备证明的是"这些点真的被画到屏幕上、没出画布、跟着输入变"。两件事不要混着说。**

**留给用户的一个决定。** 世界层给试剂瓶用的是 `Glassware.beaker100()`(矮粗烧杯),
39° 时看起来像培养皿,水平不水平靠眼睛读不出来。换细口瓶剖面会改到
`PourModel.flowRate` 读的 `liquidHeight`,也就是改倾倒流速和这道题的耗时 ——
那是判据相关的量,不该由实现层顺手定,故未做。
